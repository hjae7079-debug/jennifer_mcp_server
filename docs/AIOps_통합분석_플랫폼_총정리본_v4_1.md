## 1. 목표

## 4. 데이터 원천과 수집 방식

### 4.1 ITSM (장애·이벤트·VM·업무)
| 대상 | 주요 필드 | 수집 주기 |
|---|---|---|
| 장애·이벤트 | ID, 발생·변경 시각, 내용, 등급, 관련 VM·업무·URL | **5분마다 신규 감지** (신규는 분석 큐에 등록) |
| VM 정보 | VM ID(예: vm00012345), IP, 호스트명, NAT IP, 소속 업무명, CPU, 메모리, 할당 정보 | **하루 1회 전체 비교** (새벽 01:00) |
| 업무 정보 | 업무 ID, 기관명, 업무명, 도메인, URL 목록, 소속 VM 목록 | **하루 1회 전체 비교** |
| 기타 ITSM 정보 | 조치·변경 이력 등 | 추후 DB화 (보류) |

**ITSM 복사본 저장 구조**
| 테이블 | 내용 |
|---|---|
| `itsm_item` | 현재 복사본. 키는 ITSM 고유 ID. 원본 JSON, 내용 해시, 최초·마지막 확인 시각, 상태 |
| `itsm_item_history` | 값이 바뀐 필드의 이전·이후 값, 감지 시각, 실행 ID |
| `itsm_sync_run` | 실행 기록(신규·갱신·삭제 의심 건수, 완료 또는 부분 실패) |
| `platform_overlay` | 관리자의 매핑·메모 등 보정 값. **복사본은 덮어쓰지 않음** |

**일일 전체 비교 규칙**
- 목록을 끝까지 페이지 단위로 받은 실행에서만 삭제를 판정합니다. 중간에 실패하면 삭제 판정 없이 재시도합니다.
- 내용 해시가 다르면 갱신하고 이력을 남깁니다.
- 분석에 쓰는 필드가 바뀌었을 때만 재분석 큐에 넣습니다. 기존 분석은 보존합니다.
- ITSM에서 사라진 건은 **삭제 의심**으로 표시하고, 연속 2회 비교에서도 없으면 **삭제 확정**으로 바꿉니다. 행은 지우지 않습니다.

**ITSM 호출**: 실패 시 최대 3회 재시도(1분, 3분, 5분). 연결이 복구되면 마지막 성공 시점부터 보충 수집합니다.

> 확인 필요: ITSM 응답에 수정 시각 필드와 페이징 방식이 있는지는 샘플을 받은 뒤 확정합니다. 없으면 "최근 N일 재조회" 방식으로 바꿉니다.

### 4.2 Jennifer (WEB/WAS/DB 성능)
**확인된 사양 (실측, 5.6.3.13, 2026-10-14)**
- 도메인 51개 (에이전트 있는 도메인 33개), 인스턴스 308개 (LIVE 297, STOPPED 11). 전부 JAVA.
- 인증: `Authorization: Bearer <토큰>`. 쿼리 스트링 토큰은 접근 로그에 남으므로 쓰지 않습니다.

**실측 제약과 설계 반영**
| 실측 | 설계 반영 |
|---|---|
| dbmetrics는 지표를 1개만 받음 (2개면 500) | 지표마다 호출. 호출 수는 인스턴스 × 지표 수 ÷ 주기로 계산 |
| status/* 시작·끝이 정시(분·초 0)여야 함 | 조회 구간을 분 단위 정시로 맞춤 |
| status/* sort_by_metrics=responseTime → 500 | 정렬은 /api/metrics에 있는 지표 이름만 사용 |
| status/* instance_id 필터 → 0건 | 인스턴스 단위는 dbmetrics/instance 또는 realtime/instance 사용 |
| transaction/time은 구간 60초 이하, 1분 약 7,280건(3.9MB) | 원시 트랜잭션 대량 수집 금지. 장애 분석은 status 집계 + 대표 txid 소량 |
| transaction/txid는 time에 endTime 필요, instanceOid=0 (서버 버그) | 인스턴스 식별은 instanceId |
| realtime/instance 4~5초 | 5분마다 전수 호출 금지. 업무에 연결된 인스턴스만 |
| dbsearch의 time은 Java Date 문자열 | 저장 전 epoch ms로 변환 |
| 프로파일 GAP은 바로 위 단계가 쓴 시간 | 프로파일 해석 규칙으로 명시 |
| clientIp, clientId는 개인정보 | 저장하지 않고 MCP 응답에서도 제외 |

**호출 정책 (2026-11-01 결정)**
- 공식 명세의 GET 엔드포인트를 전수 호출하고, 파라미터 경계 케이스도 확인합니다.
- **차단**: 모든 POST·PUT·DELETE, `/api-v2/manage/*`, `/restapi/*`, 사용자 목록(`/api/auth/userlist*`).
- 조회 전용 토큰은 발급받을 수 없어 **현재 토큰으로 진행**합니다. 그래서 코드 차단 규칙을 단위 테스트로 검증하고, 모든 호출을 로그로 남깁니다.

**Jennifer 어댑터 장애 격리 (D-10)**: 서버 3대(인터넷, 행정, 대민)마다 타임아웃과 토큰을 분리합니다. 응답이 없으면 건너뛰고 "조회 불가(서버명, 사유)"를 결과에 표시합니다.

**명세 상태**: 공식 Open API 명세(Swagger)를 확인했습니다. 조회 API 대부분이 `/api/*`(v1)입니다. 명세 설명에는 v1이 "더 이상 유지보수되지 않는다"고 되어 있으므로, 벤더 업그레이드 때 깨질 수 있다는 위험을 기록합니다.

### 4.3 SIEM (로그·보안·접근·자원)
- 조회 키 우선순위: VM ID → IP(내부·NAT) → URL·호스트명.
- 기본 시간 범위: 장애 시각 전후 ±30분 (관리자가 변경 가능).
- 결과는 **요약과 조회 조건(키, 기간, 건수)만 저장**하고 원본은 저장하지 않습니다. 같은 조건을 다시 재현할 수 있게 하기 위해서입니다.
- 정규화 스키마: log_type, event_time, src_ip, dst_ip, action, raw_ref.
- 상세 API 명세와 응답 샘플은 폐쇄망에서 받은 뒤 확정합니다.

## 5. 매핑 체계 (오분석 방지의 핵심)

장애가 어느 서버에서 났는지 찾는 경로는 다음과 같습니다.

```
장애 레코드 → 업무 ID · 도메인 · URL
     ↓ (URL 정규화: 스킴 제외, host+path)
url_vm_map (URL ↔ VM, 1:N)  — 출처: ITSM 업무의 VM 목록
     ↓
vm_address (VM ↔ IP, NAT IP, 호스트명)
     ↓
jennifer_instance_map (VM ↔ Jennifer 인스턴스, 매칭 방식·신뢰도)
     ↓
분석 대상 인스턴스 → 지표·집계·이벤트 조회 → SIEM 조회(VM ID/IP/URL, ±30분)
```

**규칙**
- 한 URL에 VM이 여러 개면 **후보 VM 전부를 분석**하고, 근거마다 어느 VM인지 구분해 표시합니다(D-16). 하나로 확정하지 않습니다.
- 같은 IP가 여러 업무에 묶이면 후보를 모두 표시합니다.
- 매핑마다 신뢰도를 기록합니다: 자동 일치, 후보 다수, 수동 확정.
- 신뢰도가 낮으면 근거에 "대상 불확실"을 표시합니다.
- 관리자의 수동 매핑은 `platform_overlay`에 두고, 자동 매핑보다 우선합니다.
- 분석 시점의 매핑 결과를 `analysis_snapshot`에 저장합니다. 나중에 매핑이 바뀌어도 당시 기준을 확인할 수 있습니다.

## 6. 동작 방식

### 6.1 장애·이벤트 자동 분석 흐름
1. 5분마다 ITSM 신규 장애·이벤트를 감지해 `itsm_item`에 넣고 분석 큐에 등록합니다.
2. 장애의 업무·도메인·URL로 매핑을 찾습니다(5장).
3. Jennifer에서 대상 인스턴스의 지표와 집계를 조회합니다. 서버별 타임아웃과 격리를 적용합니다.
4. SIEM에서 장애 전후 ±30분 로그를 조건(VM ID, IP, URL)으로 조회합니다.
5. 조회 결과를 **코드가 먼저 집계**합니다. 이상 구간을 찾고 대표 샘플만 뽑습니다(D-06).
6. 요약을 LLM(Qwen3 14B)에 넣고 원인 후보를 만들게 합니다. 입력 데이터는 "데이터 영역"으로 감싸 명령으로 해석되지 않게 합니다(D-07).
7. **근거 검증**: 원인 후보마다 근거 ID가 있어야 하고, 그 ID가 이번 분석의 실제 데이터에 있어야 합니다. 검증에 실패하면 저장하지 않고 "근거 부족" 상태로 둡니다(D-05).
8. 기대 조치, 영향 범위, 불확실성을 정리해 저장합니다. 분석 상태는 "완료"가 됩니다.
9. 운영자가 상세 화면에서 검토합니다. 승인 전까지 공식 분석이 아니며, 승인된 결과만 유사 사례 검색에 쓰입니다.

**분석 결과 구조(JSON 개념)**
```json
{
  "summary": "...",
  "causes": [
    {"title": "...", "evidence_ids": ["ITSM-...", "JEN-...", "SIEM-..."], "confidence": "low|medium|high"}
  ],
  "impact": {"institutions": [], "businesses": [], "services": []},
  "recommendations": ["..."],
  "uncertainty": ["..."],
  "missing_data": [{"source": "SIEM", "reason": "조회 실패: 타임아웃"}]
}
```

### 6.2 기본 분석과 심화 분석
- **기본 분석**: Qwen3 14B 단일 호출. 대부분의 장애를 처리합니다.
- **심화 분석(2차)**: 원인 후보가 불명확하거나, 데이터가 부족하거나, 영향도가 높거나, 여러 시스템에 전파됐거나, 결과가 충돌할 때 Dify 워크플로로 다단계 분석합니다.
- 원인을 확정할 수 없으면 추측하지 않고 **불확실성을 표시**합니다.
- 분석 목표 시간: 기본 분석 약 3~5분(실측 후 확정).

### 6.3 관찰대상 자동 탐지 (탐지내역 이전 단계)
- 장애나 이벤트가 되기 전의 징후를 **규칙 기반**으로 찾습니다. 운영자가 대상을 고르지 않습니다.
- 예시: 힙 사용량이 며칠 전까지 정상적으로 반환되다가 최근 지표에서 상승 추세를 보이는 경우, GC 시간 비율 상승, 응답시간 추세 변화, DB Pool 사용률 상승.
- 탐지 기준: 기준선 대비 변화율이나 최근 기울기가 일정 기간 이상 지속될 때.
- 하루 등록 상한과 같은 인스턴스·지표의 중복 등록 제한을 둡니다. 알림 피로를 막기 위해서입니다.
- 상태: 관찰 중 → 재확인 → 종료. 종료 후에도 이력은 남깁니다.
- 1차에 포함하며, 지표 시계열 수집(ClickHouse)도 함께 구현합니다.
- 2차에는 통계 기반(요일·시간대 기준선)으로 확장합니다.

### 6.4 탐지내역
- AI가 자동 탐지한 결과를 **시간순 로그**로 기록합니다. 행을 누르면 분석 상세로 이동합니다.
- 항목: 탐지 시각, 기관명, 업무명, 분석 결과 요약, 상태.

### 6.5 수동 분석
- 사용자가 드롭다운으로 조건을 고릅니다.
  - **기관 → 업무 → 시간** 또는 **기관 → 시간**(기관 전체)
- 시간 범위 최대 **7일**. 7일을 넘으면 접수하지 않습니다.
- 같은 조건(기관·업무·시간이 정확히 같음)이 **24시간 안에** 다시 요청되면 기존 결과를 보여줍니다. 새로 분석하려면 명시적으로 요청해야 합니다.
- 7일 조회는 SIEM과 GPU 부하가 크므로 ClickHouse 집계 후 기간을 나눠 요약하고 합칩니다. 원본은 저장하지 않습니다.
- 작업 우선순위: 장애 분석 > 수동 분석.
- 사용자 한 명당 동시 1건.
- **결과 공개**: 요청자 본인에게만 보입니다. 승인자가 승인하면 공식 분석으로 전환됩니다.
- 수동 분석 결과와 자동 탐지 결과가 다를 수 있습니다. 차이 이유는 아래 6.6을 봅니다.

### 6.6 같은 조건에서 결과가 같은가
| 구분 | 같은 결과 | 달라질 수 있는 부분 |
|---|---|---|
| 근거 수치(평균 응답시간, 증가율 등) | 같은 데이터면 항상 같음 | 데이터가 늦게 들어오면 차이 |
| 매핑 | 탐지 당시 스냅샷 기준 | 수동 분석은 현재 매핑 기준 |
| 원인 후보 순서·문장 | 달라질 수 있음 | LLM 특성 |

**설계 원칙**: 수치와 규칙 판단은 코드가 먼저 계산하고, AI는 설명만 합니다. 그래서 근거 수치는 항상 같고, 문장만 달라질 수 있습니다.

### 6.7 채팅 (Open WebUI)
- 일반 사용자는 Open WebUI에 로그인해 Qwen3 14B와 채팅합니다.
- 채팅 사용자도 장애·이벤트를 **전체 조회**할 수 있습니다(D-19). 최종 검토 후 유지합니다.
- 채팅 계정과 대시보드 계정은 **분리 운영**합니다. 관리자가 계정을 만듭니다. 공개 가입은 막습니다.
- 권한 연결: 관리자가 **매핑 표**(채팅 계정 ↔ 권한 역할 ↔ 사용자별 API 토큰)를 관리합니다. 누가 무엇을 조회했는지 추적할 수 있습니다.
- Open WebUI가 사용자별 토큰을 도구 호출에 넘길 수 있는지는 **설치할 버전에서 확인**해야 합니다.

## 9. 보안

| 항목 | 설정 |
|---|---|
| 외부 노출 | 18080, 18081만. 허용 대역에서만 접근 |
| 대시보드 인증 | Nginx 기본 인증(htpasswd) + HTTPS |
| Open WebUI 인증 | 자체 로그인 + HTTPS. 공개 가입 차단 |
| 통신 암호화 | TLS 1.2 이상. 자체 서명 인증서(SAN에 폐쇄망 IP 포함). 기관 CA가 있으면 교체 |
| Nginx 허용 경로 | /api/dashboard, /api/items/, /api/integrations/status, /healthz만 전달. 나머지 /api/*는 404 |
| 차단 경로 | /api/chat, /api/embeddings, Jennifer 탐색 API는 외부에서 직접 호출 불가 |
| FastAPI | 127.0.0.1:18000 (관리자 SSH 터널). `/docs`, `/redoc`, `openapi.json` 비활성 |
| 내부 서비스 | Ollama, DB, Redis, ClickHouse는 호스트 포트 없음 |
| 비밀값 | `.env`는 root:root 600. git과 백업에 넣지 않음. DB 비밀번호는 자동 생성 |
| 인증서 키 | `/data/certs`, 600. git과 백업에서 제외 |
| 외부 연동 | 읽기 전용. 호출 허용 목록(GET만). 쓰기 차단 규칙은 단위 테스트로 검증 |
| 프롬프트 인젝션 | 수집 데이터를 데이터 영역으로 구분. 의심 패턴이 있으면 결과에 경고 표시 |
| 방화벽 | ufw 기본 차단. 필요한 포트만 허용 |
| 감사 | 조회, 작성, 승인, 반려, 설정 변경 기록 |

**알려진 한계**: HTTPS 인증서가 자체 서명이므로 사용자 PC에 신뢰 등록이 필요합니다. 기본 인증은 임시 방식이며 RBAC와 통합 로그인(SSO, LDAP/AD)은 2차에 도입합니다.

## 12. 설치와 폐쇄망 전환

### 12.1 방식
- 같은 GPU PC를 **인터넷망에서 설치·검증**한 뒤 IP와 네트워크만 바꿔 **폐쇄망에서 기동**합니다.
- 인터넷은 **네트워크 장비(NAT)로 목적지를 제한**해서 설치 기간에만 허용하고, 설치 후 차단합니다.
- 폐쇄망에서도 pip, npm, Docker 재빌드가 막히지 않도록 **오프라인 번들**을 미리 만듭니다.
- 연동 샘플 수집은 **폐쇄망 이전 후**에만 가능합니다.

### 12.2 단계
| 단계 | 작업 | 주요 스크립트 |

| 1 | 외부 통신 확인 | 매뉴얼 4장 |

### 12.4 설치 후 설정 원칙
- 커널과 NVIDIA 드라이버는 `apt-mark hold`로 고정합니다.
- 자동 업데이트(unattended-upgrades)는 끕니다.
- 코드 변경은 `IMAGE_MODE=dev`에서 컨테이너 재시작만으로 반영합니다. 릴리스 때는 `release`로 이미지를 고정합니다.
- Docker의 `system prune -a`는 금지합니다. 기반 이미지가 지워지면 폐쇄망에서 재빌드할 수 없습니다.

## 13. 연동 개발 방식

1. 제니퍼: 명세 기준 GET 전수 호출 → 샘플 수집 → 래퍼와 명세 대조 보고서 → 필요한 기능만 구현
2. ITSM: 샘플 수집 → 필드 매핑(설정 파일) → 일일 전체 비교 구현
3. SIEM: 샘플 수집 → 검색 조건 확정 → 대용량 제한 적용
4. 설정 파일에 매핑을 두고, 코드 수정은 최소로 합니다.
5. 샘플은 마스킹 후 `tests/fixtures/`에 저장하고, 단위 테스트에 씁니다.
6. 어댑터는 설치 직후 **꺼진 상태**로 두고, 차단 규칙 테스트와 샘플 확인이 끝나야 켭니다.

### 14.1 그 밖의 확정 사항
- 메뉴 이름: 이미지 기준(홈, 장애분석, 이벤트분석, 탐지내역, 관찰대상, 이력관리, 설정) + 수동분석 추가
- KPI: 당일 24시간 발생 건수 (이미지의 "최근 1시간"은 수정)
- 장애분석·이벤트분석: 목록 + 필터(기간, 기관, 상태) + 상세
- 관찰대상: 운영자 등록이 아니라 자동 탐지 후보. 1차에 규칙 기반 포함
- 수동분석: 드롭다운 조건, 최대 7일, 같은 조건 24시간 재사용, 요청자 본인에게만 공개
- 역할: 관리자(전체), 사용자(조회·요청·검토)
- 승인: 사용자는 의견 작성, 관리자만 승인·반려
- 재분석: 요청자 본인 가능
- ITSM 원본은 GPU PC에서 수정 불가. 복사본과 보정은 플랫폼 내부에서만
- Jennifer 호출: 명세 기준 GET 전수 + 쓰기 차단 + 사용자 목록 제외. 현재 토큰 사용
- 채팅 계정: 대시보드 계정과 분리, 관리자가 생성
- 연동 샘플: 폐쇄망 이전 후 수집
- 설치: 기반 설치 먼저, 연동 명세는 병행
- NAT: 네트워크 장비에서 설치 기간에만 필요한 목적지만 허용

| 자체 서명 인증서 | 브라우저 경고 | 사용자 PC 신뢰 등록, 기관 CA 전환 |
| 기본 인증이 임시 방식 | 사용자 관리 부족 | RBAC·SSO는 2차에 도입 |
| 커널·드라이버 자동 업데이트 | GPU 장애 | `apt-mark hold`, 자동 업데이트 끄기 |
| 데이터 누적으로 디스크 부족 | 서비스 중단 | 경보(80%, 90%), 정책 확정 후 정리 |

## 18. 용어

| 용어 | 뜻 |
|---|---|
| 복사본 | ITSM 원본을 읽어 PostgreSQL에 저장한 것. 원본을 수정하지 않음 |
| overlay | 관리자의 보정 값. 복사본을 덮어쓰지 않고 따로 저장 |
| 매핑 스냅샷 | 분석 시점의 URL→VM→인스턴스 연결 상태 |
| 근거 ID | 분석 결과가 참조하는 데이터 항목의 고유 번호. 검증 대상 |
| 관찰대상 | 장애 전 징후를 규칙으로 찾은 후보 |
| 탐지내역 | AI가 자동 탐지한 결과의 기록 |
| 수동분석 | 사용자가 조건을 골라 직접 요청한 분석 |
| 공식 분석 | 승인된 분석. 지식(유사 사례 검색)에 포함 |
| 전체 비교 | 하루 1회 ITSM 목록 전체를 복사본과 대조하는 작업 |
| 신규 감지 | 5분마다 최근 장애·이벤트만 확인하는 작업 |
| 데이터 영역 | LLM 입력에서 수집 데이터를 명령과 구분해 감싸는 영역 |
